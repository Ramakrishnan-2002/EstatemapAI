# EstateMap AI — Architectural Decisions & Engineering Tradeoffs

| Decision Area | Chosen Architecture | Alternatives Considered | Primary Rationale | Tradeoff & Limitations |
| :--- | :--- | :--- | :--- | :--- |
| **Spatial Database** | PostgreSQL 16 + PostGIS 3.4 | MongoDB Geospatial, MySQL Spatial | Tight integration with relational schema, ACID consistency, GiST spatial indexing, robust geography spheroidal calculations | Adds database indexing complexity and PostGIS extension requirement |
| **Spatial Filtering** | Server-side Database (PostGIS) | Client-side JavaScript filtering | Correctness, scalability, and memory efficiency | Requires backend network requests for viewport recalculations |
| **Map Transport** | GeoJSON (RFC 7946) | Vector Tiles (MVT / Mapbox Vector Tiles) | Simple, typed, lightweight, and appropriate for current dataset sizes (< 5,000 properties) | Less efficient for rendering hundreds of thousands of simultaneous features (addressed in future scale phase) |
| **Search Trigger UX** | Explicit "Search This Area" button + debounced viewport bounds | Query on every map movement frame | Prevents network thrashing and unnecessary backend database load during active panning | Requires one user click interaction to refresh area results |
| **Coordinate System** | WGS84 (EPSG:4326) with `[lng, lat]` GeoJSON | Web Mercator (EPSG:3857) or custom projected CRS | Universal standard for GPS and GeoJSON web clients | Requires geography casting for meter-based distance computations |
| **POI Categories** | Python StrEnum + CheckConstraint | Dynamic `poi_categories` table | Compile-time safety across Pydantic & TypeScript, zero JOIN overhead on spatial queries | Requires code deployment and migration to alter categories |
| **POI Proximity Distances** | Dynamic PostGIS `ST_Distance` on geography | Stored scalar distance columns on Property | Guarantees zero stale data when POIs are added/updated; single source of truth | Computes distance at query time (mitigated by GiST index) |
| **POI Relationship Model** | Pure spatial relationship (no FK / junction table) | `property_pois` junction table | Decoupled entities; spatial proximity is continuous and dynamic | Cannot store custom manual overrides per property without new model |
| **Location Intelligence Queries** | Sequential per-category PostGIS queries | Parallel queries sharing one `AsyncSession` | Thread-safe database session lifecycle, zero connection pool contention, runs in < 15ms | Does not parallelize query I/O across threads on a single session |
| **POI Data Sourcing** | Deterministic demo seed fixtures | Live third-party APIs (Google Places, OSM) | 100% reproducible tests, zero external API costs or rate limits, geographic alignment with listings | Static demo dataset until external ingester pipeline is added |
| **Property Ranking Engine** | 2-Stage Deterministic Scoring (`utils/ranking.py`) | Vector embeddings / LLM-based ranking / Blackbox ML | 100% reproducible, explainable, sub-10ms latency, zero hallucinations, strict hard constraint guarantee | Linear weighted sum does not learn non-linear user behavior implicitly (addressed via explicit weight tuning) |
| **Candidate Pool Bounding** | Strict `MAX_RANKING_CANDIDATES = 50` pool | Scoring entire database in memory | Prevents CPU starvation and N+1 road network routing latency | Properties ranked beyond top 50 hard database candidates are not evaluated in Stage 2 |
| **Missing Data Policy** | Proportional Weight Redistribution | Imputing synthetic default values or zero score | Never penalizes properties when user omits optional criteria or commute target | Unspecified criteria have zero impact on relative ranking score |
| **Redis Cache Keys** | Canonical deterministic serializer with 4-decimal coord rounding | Freeform string templates / URL query string hashing | Prevents cache fragmentation across equivalent floating point bounds | Slightly rounds spatial precision for caching (within ~11 meters) |
| **AI Architecture** | "LLM interprets, Backend decides, Database owns facts" | End-to-end Text-to-SQL / Autonomous AI agents | 100% elimination of SQL injection, zero hallucinations of factual property attributes, predictable API latency | LLM cannot generate arbitrary ad-hoc analytical queries on uncharted tables |
| **Local LLM Model** | Local `llama3.2:3b` via Ollama JSON mode | Cloud-only proprietary APIs (OpenAI / Anthropic) | Zero API token costs, complete data privacy, offline capable, zero external network dependency | Local inference takes ~2.0-3.5s latency per query on standard hardware |
| **Multi-Provider Routing** | Deterministic `AIRoutingPolicy` (Ollama for standard, Gemini Flash for complex) | LLM-based agent routers / Random routing / Cloud-only | Predictable latency & cost, zero recursive LLM calls, zero network calls on simple/adversarial queries | Requires tuning complexity thresholds (constraint counts, query length) |
| **Multi-Property Comparison** | Hybrid: Deterministic `ComparisonService` facts + LLM narrative explanation | End-to-end LLM comparison / Pure static comparison without AI | 100% elimination of arithmetic hallucinations (price/sqft, commute deltas, ranking margins); complete functionality with AI disabled | Requires explicit schema mapping between database models and prompt templates |
| **Comparison Size Limit** | Strict 2–3 properties bound ($2 \le N \le 3$) | Unbounded $N$-way comparison ($N > 10$) | High comparison readability on mobile/desktop, bounded PostGIS/OSRM query fanout, deterministic pairwise matrix | Users comparing >3 properties must execute multiple comparisons or filter down first |
| **Hosted Context Sanitization** | Allowlisted generic labels (`Property A/B/C`) without IDs/PII | Passing raw database records to cloud LLM | Eliminates cloud privacy leakage of database keys, owner details, or user PII | Hosted LLM cannot correlate external listings across distinct requests |
